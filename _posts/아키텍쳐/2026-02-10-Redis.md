##### 지금 개발하고 있는 서비스에 Redis를 적용하는 것이 올바른 선택인가?

- Redis는 어떤 서비스에 적용하는가?  
> Redis는 in-memory key-value 데이터 저장소로 지연(latency)을 최소화해야 하는 시스템에서 사용

  1. 캐시 (Cache)
     - DB 조회 결과, 외부 API 응답, 연산 결과를 메모리에 저장
     - TTL (Time To Live) 설정 가능
     - 읽기 중심 서비스에서 DB 부하 감소
  2. 세션 저장소 (Session Store)
     - 웹 서비스 로그인 세션 관리
     - 분산 서버 환경에서 세션 공유
  3. 메시지 브러커
     - 간단한 이벤트 전달 시스템
     - Publish/Subscribe 패턴 지원
     - 내구성이 약하므로 고신뢰 메시징에는 Kafka/RabbitMQ가 더 적합
  4. 작업 큐
     - List, Stream 자료구조를 활용하여 비동기 작업 처리
     - Celery + Redis 조합
     - 백그라운드 분석 작업
     - 이미지 처리, 보고서 생성 등
  5. 분산 락
  6. 실시간 랭킹 / 카운터
     - Stored set (ZSET), INCR 연산 활용
     - 조회수 카운팅
     - 실시간 인기순위
  7. Rate Limiting
     - INCR + TTL 조합으로 API 요청 제한 구현
     - API abuse 방지
     - 사용자별 호출 제한
  8. 실시간 데이터 처리
     - Redis Streams:
     - 로그 수집
     - 이벤트 파이프라인
     - 경량 이벤트 처리

- 언제 Redis를 쓰는가?
  - 응답 속도가 중요한 경우
  - 반복 조회가 많은 경우
  - 상태 공유가 필요한 분산 시스템
  - `CPU-bound 작업을 비동기로 분리할 때`
  - [eventLoop + ProcessPool](https://github.com/imdsoho/CodeSnippetAPI)

##### Redis 2대 운영 시 Master-Slave 구조와 Cluster 구조 중 어떤 것이 더 좋을까?

> master-slave + Sentinel 이 "더 좋은 기본값"  
> Redis 2대를 사용하여 Cluster를 구성하는 것은 구조적으로 애매함

##### Sentinel의 역할은 무엇인가?
- Redis의 고가용성(HA)을 유지하기 위한 역할
  - 모니터링
  - 장애 판정
  - 리더 선출
  - Failover 오케스트레이션 (자동 승계)
  - 클라이언트 디스커버리 (알림/조회)
       
##### 하나의 Ubuntu 서버 안에 2대의 Redis를 운영하는 것은 어떤 이익이 있을까?

> 같은 Ubuntu 서버 안에 Redis2개만 있는 구성에서는 Sentinel의 HA 효과과 거의 없음  
> 고가용성이 아니라 프로세스 이중화임

- Sentinel이 있든 없든 `단일 장애 지점(SPOF)` 이다.

##### 하나의 Ubuntu 서버에서 Redis 운영 방법

> 이중화가 아니라 "죽지 않게 하고, 죽어도 빨리 살아나게 한다"

1. 프로세스 안정성 
   - systemd로 강제 재기동  
   <pre>ini
   [Service]
   Restart=always
   RestartSec=2  
   LimitNOFILE=100000
   </pre>
   
   - OOM 방지
   <pre>conf
   maxmemory <명확한 값>
   maxmemory-policy allkeys-lru # 캐시용도
   </pre>   
   - vm.overcommit_memory = 1

2. 데이터 안정성 **(권장)**
   - 캐시/재생성 가능한 데이터
   <pre>conf
   save ""
   apoendonly no
   </pre>
   가장 안정적 (쓰기 지연/IO 최소)
   - 유실 최소화 정책
   <pre>conf
   appendonly yes
   appendfsync everysec
   aof-use-rdb-preamble yes
   </pre>
   1초 이내 손실
   - 가열 보존 (비추천)
   <pre>conf
   appendfsync always
   </pre>
   
3. 디스크 안정성
   - Redis 데이터 디렉토리는 OS root 파티션과 분리
   - noatime 마운트
   - 디스크 full 알림 필수 (Prometheus/ Simple cron)
   <pre>bash
   df -f | awk '$5 > 80'
   </pre>
   
4. Redis 내부 보호 장치
   - 쓰기 보호
   <pre>conf
   stop-writes-on-bgsave-error yes   
   </pre>
   - 느린 클라이언트 차단
   <pre>conf
   client-output-buffer-limit normal 0 0 0 
   client-output-buffer-limit pubsub 32mb 8mb 60
   </pre>
   - Lua / blocking 명령 제한
   <pre>conf
   lua-time-limit 5000
   </pre>
   
5. 운영 가시성  
   - `redis_exporter + Prometheus + Alert 권장`
   - 필수 모니터링 지표
     - used_memory / maxmemory
     - instantaneous_ops_per_sec
     - rejected_connections
     - evicted_keys
     - aof_pending_bio_fsync
     - rdb_bgsave_in_progress
